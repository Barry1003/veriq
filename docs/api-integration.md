# API integration

Veriq and Cedar use separate backend applications and credentials. The authoritative contracts are indexed in [v0.5.0 contracts](contracts/v0.5.0/README.md); the current demo map is [LIVE-DEMO.md](../server/platform/contracts/LIVE-DEMO.md).

Veriq defaults to `NEXT_PUBLIC_DATA_SOURCE=mock`. Six read adapters now exist: overview, dashboard summary, institutional knowledge, sources, review candidates and customer interactions. They accept a server-created `VeriqApi`; they do not obtain a principal from a browser. `createVeriqApi` is server-only, accepts trusted deployment configuration, allows specific GET operations, disables caching and redirects, validates envelopes and preserves HTTP errors. It never falls back to fixtures. The dashboard composes actual `/v1/...` reads; there is no dashboard backend endpoint.

**Live Veriq pages remain blocked.** No approved authenticated browser session-to-principal resolver is implemented in this repository. The route entry points do not yet provide the required `VeriqApi`. Selecting `api` without that resolver fails closed. The remaining administration, extraction, emerging-issue and temporal views still need their own live view models. See the [repair report](integration-repair-2026-10-22.md) for the per-screen inventory.

Cedar uses server-only `CEDAR_DATA_SOURCE=preview|api`. Its environment example lists the actual server settings. Build and start with the same mode: a preview production build contains preview pages. Do not select live mode only at startup and assume those prerendered pages are connected. Configure `CEDAR_UI_ORIGIN` to the exact public browser origin; mutation checks use that trusted setting rather than Next.js’s internal request hostname. Credentials stay on the Next server. The existing shared Basic Auth gate and browser action keys are suitable only for the previously restricted synthetic environment; they do not establish separate customer/staff identities. Implement the approved identity boundary before exposing these services beyond that environment.

Transfer submission now stages the exact account, route, amount and idempotency key in an AES-GCM sealed, HttpOnly, SameSite=Strict cookie before the bank call. Production cookies require HTTPS. Configure a stable, random `CEDAR_REQUEST_COOKIE_SECRET` of at least 32 characters, separate from bearer credentials. The server binds recovery to the configured customer credential, rejects changed instructions and retains the cookie until the client has received and validated the original bank response. An uncertain request is retried with identical parameters. The cookie stores client request state; Cedar remains the authority for financial state.

Recovery covers reloads in the same browser with its cookie retained. Cookie deletion/expiry, a different device, concurrent independently staged browser tabs and rotated deployment secrets/principals require a durable server-side request registry and approved per-session mapping. Do not claim cross-device exactly-once behavior. If recovery cannot decrypt, the UI blocks another instruction and directs staff to check bank records. Support-message identity still needs equivalent durable recovery; its timestamp/body must remain unchanged on retry.

Never put application, source, connector, simulator, database or model credentials in `NEXT_PUBLIC_*`, client bundles, localStorage, URLs or logs. Backend roles, clearance, customer ownership, source grants and installation scope remain authoritative. UI guards do not replace backend authorization.
